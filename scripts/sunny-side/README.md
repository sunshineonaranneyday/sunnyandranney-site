# The Sunny Side (the store's weekly email)

`build.mjs` turns one weekly brief into the Kit-ready email, in the team's chosen design: B, "Sunny" (bold color blocks and edge-to-edge photos). `verify.mjs` holds every build to the standard below.

The email itself is `src/lib/sunny-side/email.mjs`. It's the same code the admin uses for the live preview on the weekly email page, so that preview is the email.

```
node scripts/sunny-side/build.mjs           # every brief -> out/, every stress test -> out/tests/
node scripts/sunny-side/build.mjs --tests   # the stress tests alone: no admin database, no store pages
node scripts/sunny-side/verify.mjs          # 9 renders and 6 sweeps per email; exits 1 on any failure
```

Every pull request builds the stress tests and runs `verify.mjs` on them, inside the required "Tests" check (`.github/workflows/checks.yml`), so a change to the email that breaks it on any screen can't merge. There it runs offline (`EMAIL_CHECK_OFFLINE=1`): each photo is a blank of its own shape, so the layout is the same and no image host can fail a pull request (a deleted product photo, or Shopify itself at the Medusa switch, would have failed every one). The checks of the live photos themselves (format, weight, dark artwork) run in the full check on a computer, `node scripts/sunny-side/verify.mjs` with no setting.

## Each week

1. Staci sets up the week's email at admin.sunnyandranney.com/admin/email/: the sale, 4 to 9 products from the shop, and the store's events (below).
2. Mike, the photographer, shoots the top photo, and the story photo when there is a story.
3. Fill a brief in `briefs/` with `"sale": "admin"`, `"wall": "admin"` and `"events": "admin"`, then build, verify, and test-send to Peter's inbox through Cloudflare Email Sending. Staci and Holly approve the test, then it goes into Kit.

`"admin"` makes the build read what Staci saved from the store's D1 database, using wrangler: the special and the products for the brief's `send_date`, and every event with a date still ahead on it. If she hasn't saved the special or the products yet, that brief isn't built and the build says so. `--local` reads the local dev database instead (`node scripts/sunny-side/build.mjs --local brief.json`). The sale, the products and the events are Staci's to set there; a brief never asks anyone else for them.

The build tries every brief, so one waiting on the admin doesn't hold up the rest, then lists any it couldn't build and exits 1. A brief that fails, or is gone, leaves no old email in `out/`, and every build leaves only its own emails in `out/` and `out/tests/` (with `--tests` or briefs named too, which once left emails from older code for `verify.mjs` to check), so it can't pass or fail a stale one. Each built email prints its subject as it will go out.

## The brief

Every field below is used. Nothing else is read.

- `send_date` (YYYY-MM-DD): event dates before it drop out, and it names the UTM campaign (`sunny-side-<send_date>`).
- `subject`, `preheader`. Since the offer comes from the admin, they name it without typing its numbers: `{offer}` becomes the offer in a line ("Spend $250, save 10%. Spend $1,000, save 20%.", the first and last tier, or "20% off everything.") and `{upto}` its biggest percent ("20%"). Anything either line says about the discount is checked against the offer, and a mismatch stops the build: every percent off must be one the sale gives, "up to" must be its biggest, and with tiers every dollar amount must be a tier, with that tier's own percent beside it ("100% of our profits" is a share, so it's left alone).
- `sale`: `"admin"` (above) for a real week, or the offer itself (the stress tests). The offer has `name` (the small label), `cta`, `url` (a site path), optional `details` (fine print, shown under the button), and by `kind`:
  - `tiers`: `headline`, `tiers` as `[[spend, percent], ...]`, 2 to 4 of them. Four tiers, or any tier from $10,000 up, write every amount short, like `$2.5k+`.
  - `percent`: `percent`, `what` (e.g. `"everything."`)
  - `headline`: `headline`
- `hero`: `src`, `alt`.
- `wall`: `"admin"` (above) for a real week, or the wall itself: `label`, `headline`, optional `more` (the site path "Shop all" goes to; the whole shop by default, so it matches what the products are), and `photos` (4 to 9 products). Say only what's true of the picks: "Just landed" needs products that really are new. Each product is:
  - `url`: its page on sunnyandranney.com/shop/, where it can be bought;
  - optional `src`: a photo to use instead of the product's first store photo;
  - optional `name`: a short name, needed only when the store's name runs over 28 characters (the build says when).

  The build reads each product's name, price and photos from its page, the same structured data search engines read, and its stock from the shop page's own count (the number the site's filters use; a product page says "InStock" even at zero when the store sells on order). A product with none in stock, a name too long for a tile, two tiles with the same name, a PNG photo Shopify won't send as a JPEG, or a page it can't read stops the build, with every problem listed at once. A real brief can't give its own `price`; only the stress tests in `tests/` do, so they run offline. Each tile is one link: the photo, then the name in bold, then the price. The photo needs no alt, because the name under it is in the same link.
- `story` (optional): `label`, `headline`, `body`, `cta` as `[text, site path]`, and either one `photo` (`src`, `alt`) or a collage: `photos` (1 to 5, each `src`, `alt`) with an optional `layout`, one of the layouts for that many photos in `src/lib/sunny-side/collage-layouts.mjs` (`LAYOUTS`). With no `layout`, the collage is the classic one: a wide photo on top.
- `events`: `"admin"` (above) for a real week, or the list itself (the stress tests): `title`, `time` (the series' hours), optional `label` (default "Coming up"), and `items`. The line under the title is written from the dates still ahead ("Saturdays, 11am–2pm, Nov 21 to Dec 19"), so it never goes stale. With one date left there's no line, because the card says it all. Only events on different weekdays take a `when`, saying what's on ("Late shopping nights and Saturday crafts for kids"); the dates are added after it. A `when` that names a date, or a `when` on a one-weekday series, stops the build. Each item has:
  - `date` (YYYY-MM-DD; month, day and weekday come from it), `what`;
  - optional `note`, `time` (only when it differs from the series), and `greg` (Greg's photo when that date is the spotlight).
  - Optional `calendar` (weekly series only): `title`, `start` and `end` (HH:MM), `intro` (the first line of the calendar notes) and `ics` (the series' file). The Google link starts at the next date still ahead and lists only the dates left, so no one adds one that has passed. From the admin, the file is the site's `/events/<event>.ics/`, made fresh from the event with only the dates still ahead that day.
  - Optional `one` (any event): `title`, `start`, `end`, and the event's `site` and `id`. The card that leads the event gets links for its next date alone; Apple and Outlook get that date's own file, `/events/<event>/<date>.ics/`. Every address on the site that an email points at ends in a slash (`addresses.mjs`): the site uses `trailingSlash: 'always'`, and in production a file address without one matches no route and gets the 404 page.
- `mission`: the charity section.
  - `photo` (`src`, `alt`): the latest reveal.
  - `caption`: who's in it, like "Remi and Nico, ages 14 and 12, in their new bathroom."
  - `story`: two sentences on what changed for them.
  - `cta`, `url`: the button and their page on sunshineonaranneyday.com.
  - `impact`: `"live"` reads the charity's room makeovers and children served from its brand page (sunshineonaranneyday.com/branding/) at build time. If it can't, the build stops rather than printing old numbers. The stress tests use fixed numbers.

Photo `src` is either a full image URL or `cf:<id>` for Cloudflare Images, which crops around the subject. Every Shopify photo goes out as a JPEG (`Email.photo` in `email.mjs`):
- Shopify resizes its JPEG, WebP, AVIF and HEIC photos and sends them as JPEGs (`format=jpg`), which Outlook can show.
- The store's own uploads (`photo:<id>`) and its Shopify PNGs go through Cloudflare's image resizing (`https://shop.sunnyandranney.com/cdn-cgi/image/…,format=jpeg,background=white/<Shopify URL>`). It runs only on hostnames Cloudflare proxies; sunnyandranney.com itself is DNS-only to the Pages site, so it's served from shop.sunnyandranney.com, the proxied hostname that redirects old shop links. Keep that hostname proxied. Shopify won't convert a PNG saved with a transparency channel, even one with nothing see-through, and Mac screenshots save one, so those came back as PNGs of 175–500KB a tile. On Nov 12, 2026, 59 of the 193 products in stock had only PNGs like that; of the 51 checked, 49 were screenshots, all fully solid.
- The domain's resizing was turned on Nov 12, 2026, in the dashboard (Images → Transformations; setting it through the API to "on" leaves it disabled). It accepts only the store's own Shopify files (`cdn.shopify.com/s/files/1/0930/2117/6092/`), so a PNG from anywhere else is left to Shopify's resizing. After 5,000 different resized images a month, Cloudflare charges $0.50 per 1,000.

`tests/` holds stress-test briefs: quiet week (one of its tiles is a screenshot PNG, so the resizing is checked on every run), four tiers, $10,000+ tiers, nine photos, events over, mixed weekdays. On their own they cover every photo-wall layout (4 to 9 photos), every tier count and all three sale kinds, so the standard is held even in a week whose brief is still waiting on the admin. They are built and verified with every run.

## The weekly email in the admin

`/admin/email/` is for managers, and it's about one email: this week's until it has gone out, then next week's (`weekToWorkOn` in `week-store.mjs`; the Today task and the sidebar mark follow the same rule). The server refuses a save, test, send or cancel for any other week. Emails already sent are read-only at `/admin/email/sent/`, read from Kit exactly as Kit sent them (tests left out), each one drawn in a script-free frame with a link to Kit's report. Staci sets up the whole email beside a live preview of it, drawn by the same code that builds it, then sends tests and schedules it to subscribers through Kit from the page. The page's sections run in the order she decides things (`PAGE_SECTIONS` in `page-email.mjs`, Peter, 2026-11-17): the subject line, the sale, the products, the reveal (which says whether the collage is needed), the photos, the events and the charity, with Send last. The error list and "Before it can go" follow the same order (`sectionOf`), and `page-order.test.mjs` fails if the page drifts from it. The preview follows the part she's working on. One Save keeps the sale and the products together; either can be saved before the other is ready. Saving checks the version the page loaded, so two managers can't overwrite each other. The Today page shows a task when that email has no sale or no products. `/admin/special/`, the page's old address, redirects here.

1. **Subject line.** The subject and the preview line. `{offer}` writes the sale in a few words and `{upto}` its biggest discount, and neither line can promise more than the sale gives (the same check the build makes). An empty preview line says the sale. The page shows how it reads in an inbox.

2. **The sale.** Three ready-made sales as cards, already filled in (Peter, 2026-11-16: "pick a ready-made sale"): tap one, change a number if needed.
   - **20% off everything**, marked the store's usual: of the 190 orders from Oct 20 to Nov 16, 2026, 148 were 20% off at the register (`USUAL_PERCENT`). It opens at the last percent the store used, else 20.
   - **Spend more, save more**, with the last tiers the store used; the first time, the amounts are hers to set (the page never invents price breaks the shop doesn't honor).
   - **No sale this week**, which shows what's new.

   A sale ends the week's Sunday unless she changes it (`usualEnds`). Nothing is written: the small label, the big line (`SALE_HEADLINES`: "Spend more, save more." / "New in the showroom this week."), the button and the fine print are the store's for each kind (`defaults` in `special.mjs`). The fine print is the terms alone: "In the showroom and online. Ends Sunday, Nov 22." A special saved before keeps none of its old headline, label, button, link, fine print or "off what".

3. **The products.** She browses the shop's own catalog (`/shop/catalog.json`, published with every deploy by `src/pages/shop/catalog.json.ts`): every product the shop lists, with its stock count and its photos' sizes. The picker works like Shopify's own: search by name, room or kind; narrow to new arrivals, staff picks or what's on sale, or by room; sort by best selling (Shopify's own ranking), newest or price; scroll through all of them; tap to add or take out. Products that are sold out show only when asked. One in stock with no photo at all shows greyed. Any photo can be picked: the email sends every one as a JPEG.

   The picks are laid out the way the email lays them out, and arranged for her: best sellers first, the widest photo leading an odd wall (a tall photo cropped 3:2 loses its top and bottom), and two of a kind never side by side when something else can go between them. She arranges them the way she arranges the collage (`Products.tsx` on `drag.ts`): she drags a product's photo to a new spot (on a phone, press and hold first), or taps it and then its new spot (the way to move them without dragging that WCAG 2.5.7 asks for), or uses the keys; each has an × to take it out, and every change says what it did, with Undo. Once she moves one, her order holds until she asks for it to be arranged again. She can pick which of a product's photos the email shows. A name too long for a tile gets a suggested short name when one can be made cleanly ("Hamlin Swivel Chair, Beamer Blue" becomes "Hamlin Swivel Chair"), or a field for hers. Two tiles can't say the same name. The words over the products default to "Shop the floor / Our picks this week." and can say "new" only if every product was added in the last 30 days.

4. **The reveal.** In a week with a charity reveal coming, the charity's invite to watch it live, in the charity's own words, photo, day and time, or none. It's its own section of the email, right under the story: it never takes the story's or the collage's place (Peter, 2026-11-17: "its not a either or"). A week saved before then with the reveal inside the story (`story.reveal`) reads as both.

5. **The story.** A small label, a headline, two or three sentences, and a link to a page on sunnyandranney.com, with the collage under it. A week with a reveal can go without a story; once the story has anything in it, it needs its headline and words.

6. **Photos.** She uploads the week's photos from a phone or computer, through a drop zone always in view (a dashed box: "Add photos or drag them here"; a click anywhere in it opens the file chooser, and a drop anywhere on the section counts). The browser shrinks each to a JPEG at most 2,400 px across before it goes up (a phone's 5 MB shot becomes a few hundred KB). They're kept in the R2 bucket `sunnyandranney-email-photos` (binding `PHOTOS`), with a row each in D1 table `email_photos` (`photo-store.mjs`), and served at `/media/email/<id>.jpg`. The email asks for them through the domain's resizing (`photo:<id>` in `Email.photo`), cropped to each spot around what's in them, or around the part she chose (below). Each photo has a few words saying what's in it, for people who can't see images. She picks one as the top photo (or keeps the store's wide shot) and up to 5 for the story's collage, in the order she wants. A photo the store doesn't need goes with the bin on its corner (or Delete photo in its sheet), which opens its sheet at "Delete it for good?" with Keep and Delete (no browser dialog), the photo big so there's no doubt which one: it leaves the library, and one in this email comes out of it on the page (Save keeps that). Its file is deleted too, unless an email scheduled or sent through Kit uses it (`photoInKitEmail`): that email asks the site for the photo every time someone opens it.

   The collage comes in a choice of bento layouts for each number of photos (`collage-layouts.mjs`): 2 for one photo, 4 for two, 6 for three, 5 each for four and five. Every layout is drawn on the page with her own photos in it, the way Instagram's Layout app showed its layouts, and switching keeps her photos and their order, as Google Photos' collage editor does. The one that keeps the most of her photos (each photo's share left after cropping to its spot, weighed by how big the spot is) is marked "Best fit", and it's what the email uses until she picks. On the week of Nov 17, 2026, the classic layout kept 62% of her five phone shots (three tall, two wide); "Three tall, two wide" keeps 82% in her order, and all of every photo after "Move them to fit", which appears whenever moving her photos to other spots in the layout keeps at least 3 points more. The collage above the choices is the chosen layout at the email's own proportions, each photo cropped to its spot the way the email crops it.

   **The library** is compact: three photos across a phone, each with its two uses as big toggles ("Top photo", "In the story"). A tap on a photo opens its details in a sheet (`PhotoDetails` in `Photos.tsx`): the whole photo, the few words saying what's in it, its two uses, and what part shows, the way Shopify keeps a photo's alt text in its media details. Press and hold (or a mouse drag) carries it up to the collage.

   **Arranging the collage** (`Photos.tsx`, `drag.ts`, `collage.mjs`). She drags a photo to a new spot and the collage lays itself out live as she holds it, so she sees which photo takes the big spot before letting go; on a phone or iPad she presses and holds a photo first, so a quick swipe still scrolls the page. While a photo is held the layout stays put (a best fit worked out again at every spot would move the spots under her finger), and an arrangement she makes by hand keeps the layout she made it in. Library photos drag up into the collage (the page scrolls when one is carried to the top edge): dropped on a spot, one goes in there while there's room, and swaps out the one there when the collage is full. Ticking "In the story" on a full collage asks which photo it replaces. Without dragging: tap a photo, then its new spot; or with the keyboard, Space picks it up, the arrow keys move it, Space puts it down, Escape puts it back, and Delete takes it out. Each photo has an × to take it out. Every change, a new layout included, says what it did, with Undo, in the collage's status line, and a screen reader hears where the photo went ("spot 2 of 3, top right, wide", from `cellWords`).

   **What part shows** (`FocusPicker.tsx`). Every photo can have a focus point (`email_photos.focus`, "0.42x0.31", added to an existing table by itself): she taps or drags to the part that matters, and the crops the email makes of it (the top photo's, and its spot in the collage) change beside it as it moves. The email sends it as Cloudflare's `gravity=XxY` (`photo:<id>@0.42x0.31` in a brief); "Automatic" goes back to `gravity=auto`. The page draws each crop with CSS `object-position` at the same point, which places a crop the way the resizing does: checked against Cloudflare's own crops of store photos, 2 shapes × 5 points, within 1px.

   A layout is a tree of cuts (Atkins, "Blocked Recursive Image Composition", ACM Multimedia 2008): photos side by side, photos stacked, or one photo of a fixed shape. Photos scale with the screen and the 4px gutters don't, so `solve()` gives every column a share of the width plus a fixed number of pixels, so both sides of every cut are equally tall at any width. The email draws each cut as its own table, with each gutter inside a table of one cell: given a row whose cells are padded unevenly, Chromium and WebKit split its width differently. `node scripts/sunny-side/collages.mjs` holds every layout to that in both engines, as sent, as Gmail shows it and bare, at every width from 320 to 700 px: every photo's edges sit on the collage's edge or face another photo across 4px, within half a pixel.

7. **Events.** Events are the store's, not one email's: each email shows the dates still ahead on its send day. An event is a name, its hours, and its dates, each with what's on, an optional note, and whether Greg's photo shows. "Add" suggests the date a week after the last one. Dates on different days of the week need a few words saying what's on (no dates in them). The card for the next date gets its own Google, Apple and Outlook links for that date alone (`/events/<event>/<date>.ics`), for any event; a series a week apart also gets links for every date still ahead, once there's more than one. Each date keeps the same calendar UID either way, so adding the date and later the series doesn't put it on a calendar twice. Each event saves on its own, and its calendar file (`/events/<event>.ics`) is made from it on request with only the dates still ahead, so it never goes stale.

8. **The charity.** A dropdown of the charity's kids; nobody at the store writes any of it. The section shows the chosen family's photo and the charity's own summary from its site, with "See their story" to their page, and the charity's numbers read live. It starts on the most recent reveal: the latest reveal date the charity has on record that has passed (its reveal invites keep them, from November 2026), and for reveals from before then, the day their photos went up (the charity's photo ids carry the time). The list is read from the charity's own database (`soard-db`, bound as `SOARD_DB`, only ever read; `kids.mjs`): its published kids that have had their reveal and have a photo and summary.

9. **Send.** Kit sends both the tests and the email, from here; nobody needs to open Kit.
   - A list says what's left before it can go, each item linking to its section.
   - **Send a test** goes to whoever's ticked: the person signed in ("You") and the store's list (Mike, Staci and Holly to start; `email_test_people`, never in this public repo). Kit's API has no test send, so a test is a small Kit broadcast of its own, a minute ahead, to just those people: each is a Kit subscriber with a tag of their own ("Weekly email test: <email>"), and someone who unsubscribed is never signed back up. It's exactly what subscribers get, with "[Test]" before the subject. At most 10 people, 20 tests a day; each test is logged (`email_test_sends`).
   - **Send to subscribers** schedules it to the store's subscribers: the Kit segment "Sunny & Ranney weekly email" (`STORE_SEGMENT`), everyone with the tag "Sunny & Ranney" (`STORE_TAG`, the tag the site's signup form adds) except those tagged "Shopify: no marketing" (2,841 people on Nov 17, 2026), at a time on its Tuesday, Eastern, starting at the time the store's emails usually go (from Kit's history). A confirmation shows when, how many subscribers, the subject and the preview line. Once it's scheduled the email is locked until it's cancelled ("Cancel the send" deletes it in Kit, until it starts sending). The Kit account is the charity's too, and a broadcast with no filter goes to the whole account, so every broadcast the admin makes, tests too, goes to its tags or the store segment and no one else: it's read back from Kit at once, and deleted if Kit didn't keep it to just them. Kit's API has no count for a segment, so the page counts it the way the segment is made (the tag less the no-marketing tag), and shows no number if Kit's filter doesn't count the no-marketing tag the same as that tag's own list (the page log says what Kit counted). Every send also goes from the store's sender, `KIT_SENDER`, a sending address confirmed in Kit; without it the admin won't send, since Kit would send as the charity.
   - Nothing is ever published to the web. Kit's docs disagree on whether sending needs "public", so every send is made with it off and read back at once: if Kit published it, it's taken off; if Kit kept it as a draft, it's deleted and the page says so. A send that can't be noted here is taken back out of Kit.
   - It goes on a Kit "Starting point" template, where the content is the whole email (`KIT_TEMPLATE_ID`, or the account's first). `kit.mjs` has the calls; `week-email.ts` builds the email for both, from what's saved, so a test is what goes out.

The rules are shared by her browser, the server and the build: `src/lib/sunny-side/special.mjs` (the sale), `wall.mjs` (the products), `events.mjs` (events and their calendar file), `catalog.mjs` (the picker's catalog). The page measures what `verify.mjs` would at 320 and 390 px, and at 320 px bare (no style block, no web fonts): the sale button on the first screen, nothing spilling, every product name within two lines. It won't save an email that fails, and it names what's too wide and where to fix it. It only ever shows what can be fixed on the page. A word in the email's own layout (its fixed words, the charity's numbers) is code, so the page never shows it to whoever is setting up the email: it reports it (`/api/admin/email/layout/`, D1 table `email_layout_reports`, `layout-store.mjs`, which creates itself), and only the owner sees it, above the preview, until they clear it. The weeks live in D1 table `email_weeks` (`week-store.mjs`), the events in `store_events` (`event-store.mjs`). Both create themselves; the first use of `email_weeks` moves any special saved in the page's older `email_specials` table over and drops that table.

Two of the stress tests use bento layouts (`edge-longest`: big beside four; `edge-mixed-days`: tall beside three), so `verify.mjs` holds them with real photos too.

The admin page itself is checked with `node scripts/check-admin-boxes.mjs <page>` against a local dev server, at eight widths from 320 to 1440 px, with every folded part open: every piece of text and every control has to stay on the box it's drawn on, no fieldset's legend may sit across its box's edge, and no text may touch the inside edge of a filled panel. A check that only asks whether the page scrolls sideways missed the story's collage label sitting half off its panel, so run this one after any change to how the page looks, once with a section empty and once full. It also fails anything past the side of the screen, and `--click "<selector>"` opens a dialog first: the product picker ran off a phone, unmeasured, until it was checked open (`--click "#em-products .em-section-tools .btn-dark"`).

On a phone the page is built to be used there (measured 2026-11-17, before → after):
- Every text field is 16px on a touch screen: iPhone Safari zoomed the whole page into the 24 smaller ones when they were tapped, and left Save off the right edge.
- Everything tapped is at least 44px each way. More than 50 controls were smaller.
- The preview is a sheet over the page: "See the preview" opens it at the part she's working on, and "Back to editing" puts her back where she was. It used to sit 11 screens down, below Send.
- The page is 10 screens long instead of 14.7.

`node scripts/check-email-phone.mjs <page>` fails any of that (16px fields, 44px targets, no sideways scrolling, the preview sheet, the length) at 390 and 320 px.

On a phone, Save moves from the page's top bar to the bottom of the screen at the first change, and the bar keeps the height it had with Save in it (`mount.ts` measures it while nothing is unsaved, `--em-bar-h`), so nothing on the page moves: it used to close up and push everything below up 56–85px, under the finger that made the change, and after a drag iPhone Safari put the page back only at the next touch, swallowing that tap. `node scripts/check-email-first-change.mjs <page>` types one letter into the preview line and presses Discard at nine widths in Chromium and WebKit, and fails if the page below the bar moved at all; `src/lib/admin/first-change.test.mjs` fails any change that moves Save without holding the bar's height.

## The standard

`verify.mjs` renders each email nine ways:
- Apple Mail's engine (WebKit) at 320 and 390 px;
- Chrome's engine at 390 px and on desktop;
- Gmail web, the Gmail app, and the Gmail app on the smallest iPhone (320 px), loaded the way Gmail serves the email: no web font, and the CSS Gmail strips taken out;
- bare, at 320 px and on desktop: no web fonts and no style block at all, the way the Gmail app shows an email to a Yahoo, Outlook or iCloud account (it keeps only inline styles).

Then it sweeps each email: as sent, as Gmail serves it, and bare, in both engines, at every width from 320 to 700 px in 10s and on both sides of each media query (374/375, 620/621), 42 widths. A sweep fails on the email running wider than the screen, on text spilling out of its box, on a button that doesn't fill its row on a phone or bare (or fills a computer's wide row), or on the directions button sitting off the address's middle beside it or other than 24 px under it, at any of them, and on any web font loading in a sweep that must have none (Gmail's and the bare ones): until Nov 16, 2026 a route sent requests past the font block, and those sweeps quietly checked DM Sans. Every render also fails if anything Staci writes or picks sits in a band without its part (`data-part`: the sale, the products, the story, the events, the charity), which is how the admin's preview knows which section a too-wide word is in. Before Nov 16, 2026 nothing checked the bare case, and the email laid out at desktop sizes on a 320 px phone ran 30 to 84 px off the screen there; and a word in the email's own fixed text ("Room makeovers", 2 px too wide in a third of a 320 px phone) was found by the admin's preview instead of here.

A render fails on any of these:
- on a phone, a sale button more than 600 px down (about what Apple Mail shows before scrolling);
- a color that isn't a brand color;
- anything off the grid: photo rows must run the full 600 px, and cards and the words that start each line must sit on the 536 px column (20 px margins on phones);
- text spilling out of its box;
- HTML code showing as text;
- a link under 44 px tall;
- heading order;
- a missing alt or a broken image;
- an image with dark artwork on a transparent background (Gmail and Outlook darken backgrounds in dark mode but never images, so that artwork disappears);
- an image that, fetched the way Outlook for Windows would (no WebP or AVIF), isn't a JPEG, PNG or GIF, or weighs over 150 KB (on Nov 12, 2026 the heaviest good image was the 103 KB hero; the screenshot PNGs were 177–493 KB);
- a photo-wall product without its name and price, or a name over two lines;
- sideways scrolling;
- two links to the same address;
- a failed request.

A source check also fails the build on CSS Gmail strips: negative margins, positioning, flex and grid. The build itself stops on a subject or preheader that promises a discount the offer doesn't give, and on a photo-wall product that's out of stock.

## Design rules

- **Colors.** Only the ones the live site shows:
  - gold #FFD400 means buy;
  - teal #2B7A96 means events;
  - charcoal #2C2C2C is for text;
  - stone #6B6B68 is for rules;
  - plus white.
- **The charity section.** Laid out like the charity's own emails (Peter, 2026-11-16: "make it top tier ... to match that from my sunshine emails"; its reveal invite, measured in Gmail that day), in its colors from sunshineonaranneyday.com and its brand guide at /branding/:
  - a Dark Deep #1E1F25 top, centered: the guide's display logo for dark backgrounds (`brand-logo-dark-bg-display`, cut close; yellow and white artwork, so dark mode can't hide it), "Where 100% of our profits go" in Sunshine Yellow, "Every purchase builds" in soft white italic, then "a *dream room*." with the key words in yellow italic, in Libre Baskerville;
  - the family's finished room, rounded (20 px), with its caption;
  - a cream #FEFCF5 story, led by the yellow dash and the family's name ("Remi & Nico's story"), the charity's own summary in Libre Baskerville, and a link to their page;
  - then its impact strip: Sunshine Yellow #FFDA24 numbers on Dark Deep, so the section runs dark, light, dark, as the charity's emails do.

  `verify.mjs` holds the section (class `soard`) to the charity's colors and everything else to the store's.
- **Font.** DM Sans; the charity section uses Libre Baskerville and Outfit. Outlook falls back to Arial and Gmail to Helvetica. The charity headline falls back to Georgia, but its numbers to Times New Roman, because Georgia's old-style figures made "$0" read as "$o".
- **Phones first.** Every size written inline is a phone's: type, the 20 px sides, the 32 px gaps, full-width buttons (Outlook keeps its own button). There's no max-width query at all. The style block only makes things bigger, from 375 px and on a computer (min-width:621px), and Outlook for Windows, which reads no media query, gets the computer's sizes in a block of its own. So an inbox that throws the style block away still shows an email that fits a phone, and on a computer a smaller one. Rows that sit side by side on a computer wrap by their own widths, with no media query: the visit row stacks on a phone (Rémi Parmentier's "Fab Four": min-width, max-width, width and calc, with the min-width as a share of the row, since a pixel min-width beats max-width and held a 280 px phone's column open), with a 24 px spacer between its columns worked out the same way, so it's there only while they stack (a gap hidden by a media query showed from 576 to 620 px, where they already sat side by side, and with no style block), and the charity's numbers sit three across on a computer and two plus one, centered, on a phone, as sunshineonaranneyday.com lays them out at 390 px. `phone-first.test.mjs` holds these rules.
- **Layout.** Words and cards sit on one 536 px column; photos run the full 600 px. A photo sits directly on top of the block it belongs to, and white space separates it from any block it doesn't. The photo wall's gaps sit inside its tiles, because Gmail strips the negative margins that would otherwise do it. The wall is never more than two products across, so a name and price stay readable on a 320 px phone; an odd count leads with one wide product.
- **First screen.** A slim masthead, a 2:1 top photo, and fine print under the button keep the sale button on a phone's first screen.
